# ADR-0011: Реестр плагинов и версия контракта

## Контекст

Ядро (`axislar_core`) экспортирует `IStorageEngine` и `CONTRACT_VERSION`.
Плагины — отдельные проекты, которые реализуют этот порт. Нужен механизм,
который: находит установленные плагины, не зная их имён заранее; не
позволяет несовместимому плагину уронить продукт; и не превращается в
«платформу плагинов» с собственным API-версионированием.

Требование ядра: продукт не должен импортировать внутренности плагинов и
не должен пересобираться при появлении нового бэкенда.

## Решение

1. **Обнаружение — через entry points**, группы:
   - `agoralar.storage` — бэкенды `IStorageEngine`;
   - `agoralar.source` — адаптеры внешних источников (позже).
   Плагин объявляет точку входа в своём `pyproject.toml`:

   ```toml
   [project.entry-points."agoralar.storage"]
   json = "agoralar_store_json:create"
   ```

2. **Контракт плагина — функция-фабрика + манифест.** Точка входа
   возвращает `PluginManifest`:

   ```
   name: str                  # "json"
   kind: storage | source
   requires_contract: str     # PEP 440 specifier, например ">=2,<3"
   factory: Callable[[dict[str, Any]], IStorageEngine]
   ```

   Никаких базовых классов «плагина» и реестров внутри плагина.

3. **Проверка совместимости — по `CONTRACT_VERSION` ядра** через
   `packaging.specifiers.SpecifierSet`. Несовместимый плагин не грузится,
   но и не ломает продукт: попадает в `rejected` с причиной
   (`requires_contract`, фактическая версия).

4. **Ленивая загрузка.** Реестр читает только метаданные entry points;
   модуль плагина импортируется в момент выбора бэкенда. Ошибка импорта
   плагина — тоже `rejected`, а не падение продукта.

5. **Реестр живёт в продукте** (`beta`), а не в ядре: ядро не знает про
   entry points и про существование продукта.

6. **Версионирование.** `CONTRACT_VERSION` ядра — целое (`2`).
   Диапазон продукта — `CORE_CONTRACT_RANGE` в `mu` продукта. Плагин обязан
   удовлетворять обоим: своему `requires_contract` и диапазону продукта.

## Альтернативы

- **Явный список плагинов в конфиге без обнаружения.** Просто, но требует
  ручной правки конфига на каждый плагин и не даёт «поставил — работает».
  Отклонено; конфиг остаётся для включения/выключения уже найденных.
- **Реестр в ядре.** Ядро узнало бы про установленные пакеты и группы
  entry points — протечка продуктового понятия в модель. Отклонено.
- **Плагины как подпакеты продукта (`agoralar.plugins.json`).** Смешивает
  продукт и сторонние пакеты, ломает независимый деплой плагинов.
  Отклонено.
- **Проверка совместимости по версии пакета (`axislar-core>=0.2`).**
  Версия пакета и версия контракта живут по-разному (патч-релизы не меняют
  контракт). Отклонено: у плагина должен быть один адресат — контракт.

## Последствия

Плюсы: продукт не пересобирается при появлении плагина; несовместимость
видна как данные, а не как трейсбек; ядро остаётся чистым; сторонний
плагин проверяется тем же контрактным набором.

Минусы: нужна зависимость `packaging` в продукте; entry points — «магия»
при отладке (поэтому есть команда `plugins list` с причинами отказа);
плагин обязан объявлять `requires_contract`, иначе считается
несовместимым (fail-closed).

## Статус

Принято.
