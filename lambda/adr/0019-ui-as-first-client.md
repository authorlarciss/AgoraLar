# ADR-0019: UI — первый клиент, а не надстройка

## Статус

Принято. Реализация — фазы 1–5 (`lambda/PLAN.md` §3).

## Контекст

До сих пор единственным клиентом был CLI. Это нормально для ядра и плагинов,
но не для продукта: задача проекта — «упорядочить свой архив», а это
пространственная, визуальная задача. Пока основная работа идёт через
терминал, мы продаём API, а не порядок. Владелец проекта (как пользователь,
а не как разработчик) сформулировал это прямо: без удобного интерфейса он
сам не стал бы пользоваться продуктом, каким бы хорошим ни был функционал.

Одновременно есть риск впасть в другую крайность: «сделать красивый UI» и
потерять модель — то, ради чего всё строилось. Поэтому решение фиксирует не
только «делаем UI», но и границы.

## Решение

1. **UI — первый клиент, но не второй источник истины.** Никакой доменной
   логики во фронтенде: каждая кнопка вызывает use-case в `beta`, который
   использует контракты ядра. Если чего-то нет в use-case, значит этого нет
   и в UI.
2. **Паритет с CLI.** UI не умеет ничего, чего не умеет CLI, и наоборот.
   CLI остаётся эталонным клиентом для e2e-тестов; UI проверяется через
   HTTP API. Одна семантика, две поверхности.
3. **Только чтение первым.** Первая версия: список с фильтрами по осям,
   карточка объекта, связи, карта разреженности, скачивание артефакта.
   Редактирование — после ревизий и отката (фазы 2–3): редактор без undo
   для этой аудитории опасен.
4. **Модель показывается, а не прячется.** В интерфейсе видны оси,
   заполненность, пустые оси и входящие ссылки. «Просто список файлов» —
   это провал: тогда UI обесценивает ядро.
5. **Форма — локальное веб-приложение.** `agoralar serve` отдаёт статику с
   того же origin, что и API. Никакого облака: продукт про локальные файлы.
   Сборочного шага нет (vanilla JS/CSS) — пока интерфейс читает, он не
   стоит поддержки фронтенд-тулчейна.
6. **Безопасность по умолчанию.** UI доступен только на loopback и только
   на чтение, поэтому работает без токена (ADR-0017 это разрешает). Ветку
   «токен в браузере» не делаем: `sessionStorage` с токеном — это XSS-цель,
   а пользы для read-only просмотра нет. Редактирование по сети потребует
   отдельного решения (сессии, CSRF) — это фаза 3+.
7. **API версионирован.** Новые маршруты живут под `/api/v1/`; старые
   остаются работать. Для UI добавляются: список объектов с фильтрами и
   пагинацией, карточка с `ETag`, связи, статистика для карты, скачивание
   артефакта.
8. **Пагинация — offset/limit, пока нет ревизий.** Курсорная пагинация
   требует стабильного порядка при изменениях, а он появляется вместе с
   ревизиями (фаза 2). Read-only UI живёт с `offset/limit`; переход на
   курсоры — часть фазы 2, не отдельное решение.

## Альтернативы

- **Desktop-приложение сразу (Tauri/Electron).** Дороже, требует установки,
  и упаковывать движущуюся цель бессмысленно. Локальный веб — тот же UI без
  установки; упаковка — фаза 5.
- **SPA с React/Vite.** Нужен для редактора и графа, но не для читалки.
  Сборочный шаг добавит node в тулчейн и сломает «продукт ставится одной
  командой».
- **Отдать UI стороннему проекту.** Тогда паритет с CLI and модель
  разъедутся: у нас уже был опыт двух поверхностей (CLI и HTTP), которые
  дублировали логику.
- **Токен в браузере для UI.** Отклонено: XSS-риск без выгоды для read-only.

## Последствия

Плюсы: продукт становится проверяемым на себе; use-cases выносятся из CLI,
и обе поверхности перестают дублировать логику; появляется место, где видно
модель.

Минусы: API становится контрактом, значит ядро меняется медленнее и через
версии; фронтенд придётся поддерживать (пусть и без сборки); read-only UI
создаёт ожидание «а где кнопка изменить», которое закрывается только в
фазе 3.

## Проверка

Фаза 1 считается сделанной, когда человек, не читая README, за две минуты:
открывает хранилище в браузере, фильтрует объекты по оси, открывает
карточку, видит входящие связи и видит, где в схеме дыры. Всё офлайн, одним
процессом, без установки фронтенд-инструментов.
