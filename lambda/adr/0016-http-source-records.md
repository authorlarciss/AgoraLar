# ADR-0016: HTTP-источник — JSON-записи, одна семантика с SQL

## Контекст

Плану нужен внешний HTTP-источник: данные живут в чужом API, а не в
файловом дереве и не в sqlite. Развилка: тащить произвольный REST (пути,
пагинация, вложенные объекты, идемпотентность PUT) или ограничиться тем,
что действительно нужно модели, — массивом записей в JSON.

Второй вопрос: раскладка полей по осям. У SQL-источника (0.10.0) она уже
зафиксирована: `key`, `axes`, `measurable`, `reference`, `scalars`, `multi`,
`hash`. Источник с другим набором имён заставил бы пользователя держать в
голове два словаря для одной и той же операции.

## Решение

1. **Один транспорт — один `GET`, один JSON-массив записей.** Тело запроса,
   пагинация, ретраи, авторизация по OAuth — не дело адаптера: если API
   сложнее, его приводят к массиву записей отдельным шагом (скрипт,
   прокси, `jq`). Сложность REST не просачивается в модель.
2. **Путь к массиву** задаётся `items` (`data.items`), потому что реальные
   API почти всегда заворачивают список в конверт. Это единственная
   «навигация», которую адаптер знает.
3. **Та же семантика раскладки, что у `sql`**: `key`, `axes`, `multi`,
   `measurable`, `reference`, `scalars`, `hash`. Разные транспорты — одни
   правила; README обоих плагинов ссылаются друг на друга.
4. **`null` и отсутствующее поле — отсутствие значения**, а не пустая
   строка и не ноль: фасет не создаётся (ADR-0010 ядра). Bool в
   `measurable` — предупреждение, а не `1`/`0`.
5. **`content_hash` — по сопоставленным полям.** Изменение постороннего
   поля ответа не считается изменением объекта: иначе синхронизация
   переписывала бы объекты из-за меток времени на стороне API.
6. **Ошибки транспорта — исключение `HttpSourceError` (подкласс
   `RuntimeError`)**: статус `>= 400`, недоступный хост, невалидный JSON,
   ответ не массив объектов. Прогон синхронизации падает целиком, не
   записывая половину; хранилище не трогается.
7. **Код раскладки продублирован в двух плагинах намеренно.** Плагины —
   независимые пакеты, которые не должны зависеть друг от друга или от
   продукта; общий модуль пришлось бы версионировать как отдельный
   контракт. Цена — ~90 строк, выигрыш — независимая установка. Дублирование
   контролируется одинаковым контрактным тестом (`run_source_sync_contract`)
   и одинаковыми именами опций.

## Альтернативы

- **Полноценный REST-клиент** (шаблоны URL, пагинация, POST-поиск,
  ретраи). Отклонено: это отдельный продукт-скрапер; ядру нужны объекты, а
  не универсальный HTTP.
- **Режим «AxisLar-совместимый API»** (читать `/objects` другого
  AgoraLar). Заманчиво, но это другая задача — федерация хранилищ, и ей
  нужен свой разговор про id и tombstone. Отложено.
- **Общий модуль раскладки** в ядре или продукте. Ядро не должно знать про
  «поля и колонки»; продукт не должен быть зависимостью плагинов.
  Отклонено, см. п. 7.

## Последствия

Плюсы: HTTP-источник подключается тем же конфигом, что SQL (`[plugins.http]`
+ `--option`), без правок продукта; семантика разреженности и хэша одна на
все источники; тесты без сети, на локальном сервере в потоке.

Минусы: нестандартные API требуют предварительной нормализации; нет
пагинации (большой список тянется целиком); нет ретраев и кэша; дублирование
кода раскладки. Всё это — осознанная граница «адаптер, а не скрапер».

## Статус

Принято.
