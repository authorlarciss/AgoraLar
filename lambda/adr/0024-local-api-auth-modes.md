# ADR-0024: Локальный API — режимы авторизации и адреса

## Контекст

ADR-0020 требует, чтобы меняющие запросы на loopback не мог принимать кто
угодно (CSRF), и чтобы путь к папке не приходил по HTTP. ADR-0023 объявляет
HTTP API v1 контрактом, к которому подключаются разные клиенты: браузер,
десктоп-оболочка, боты, внешний UI. Один набор правил на все случаи не
работает: браузер опирается на `Origin` и cookie, оболочка — на одноразовый
токен, сетевой режим — на Bearer, внешний UI — на allowlist.

Нужна модель, в которой режим выбран явно, а не «получилось так».

## Решение

1. **Три режима авторизации, выбираемые запуском:**
   - `serve --token <t>` (сеть, оболочка, внешний UI): каждый запрос, кроме
     `/health`, требует `Authorization: Bearer <t>`; CSRF-вопрос снимается —
     чужой странице токен неизвестен.
   - `serve` на loopback без токена (человек открыл в браузере): меняющие
     запросы проверяются по `Origin` (только loopback-хосты) и
     `Sec-Fetch-Site` (не `cross-site`); «браузерный» запрос обязан нести
     валидную сессионную cookie (`agoralar_session`, `SameSite=Strict`,
     `HttpOnly`), подделка отклоняется.
   - Внешний UI (`--allow-origin`): origin должен быть в списке; дальше —
     токен или браузерные правила, в зависимости от того, как запущен сервер.
2. **Запросы без `Origin` и `Sec-Fetch-Site` — локальные процессы.** curl,
   скрипты, CLI, боты этих заголовков не шлют, а веб-страница не может их
   скрыть. Такие запросы не блокируются в loopback-режиме: они не проходят
   через браузер, то есть CSRF к ним неприменим. Это осознанное правило, а не
   поблажка.
3. **Адрес сменный, протокол один.** По умолчанию TCP на `127.0.0.1`. Для
   оболочки и ботов допускается Unix-сокет (`--unix-socket <путь>`): тот же
   HTTP, но без порта, с доступом по правам файла (0600) — браузер до такого
   адреса не дотянется, CSRF и CORS исчезают. Это не второй контракт, а
   второй адрес.
4. **Путь к проекту не приходит по HTTP никогда** (ADR-0020): его передаёт
   оболочка через свой мост или пользователь через `agoralar open <путь>`.
5. **Правила проверяются тестами на каждый режим**, а не «на глаз»: чужой
   Origin, cross-site, подделка cookie, браузерный запрос без cookie,
   локальный без заголовков, Bearer-режим.

## Альтернативы

- **Только cookie и Origin, без токена.** Не покрывает сеть и оболочку;
  для не-loopback токен всё равно нужен (ADR-0017). Отклонено.
- **Только токен везде.** Ломает браузерный режим: страница не может
  подставить Bearer при навигации, а класть токен в URL — утечка в историю.
- **Полный отказ от HTTP в пользу IPC оболочки.** Убивает браузерный режим и
  «любой клиент» (ADR-0023), требует второго контракта. Отклонено.
- **WebSocket вместо HTTP.** Не упрощает безопасность, но добавляет push;
  возможен позже как надстройка, не как замена.

## Последствия

Плюсы: у каждого клиента явный, проверяемый режим; loopback защищён от чужой
страницы; браузер остаётся рабочим fallback’ом; оболочка не обязана светить
порт.

Минусы: три пути надо держать в голове и в тестах; UDS — дополнительный код
транспорта, когда до него дойдёт; правила нужно документировать клиентам.

## Статус

Принято. Реализация: токен-режим и правило cookie — сейчас; `--allow-origin`
и CORS — этап S2 ADR-0023; UDS — после эксперимента с оболочкой.
