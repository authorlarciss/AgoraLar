# ADR-0017: HTTP-аутентификация токеном и образ без исходников

## Контекст

ADR-0014 выпустил HTTP без аутентификации и с привязкой к `127.0.0.1`:
это было осознанное решение для локального инструмента. Следующий шаг
плана — запуск в контейнере, то есть сервис выходит за loopback. Оставлять
API без проверки в контейнере нельзя: `--host 0.0.0.0` внутри образа —
норма, а «нет аутентификации» в этом режиме означает открытый доступ к
данным.

Требования:

- одна точка отказа, без пользователей, ролей и сессий (это продукт для
  одного владельца, а не мультитенантный сервис);
- проба живости должна работать без секрета, иначе оркестратор не отличит
  «жив» от «не авторизован»;
- невозможность «забыть включить защиту» при выходе в сеть.

## Решение

1. **Bearer-токен.** `Authorization: Bearer <token>`; токен — из `--token`
   или `AGORALAR_TOKEN`. Сравнение — `secrets.compare_digest` (не по
   префиксу и не по длине).
2. **Открыт только `/health`** — проба живости: она сообщает версию,
   контракт и имя бэкенда, но не данные. Всё остальное, включая
   `/plugins` и `/artifacts`, требует токена.
3. **Fail closed на границе.** Без токена сервер по-прежнему поднимается
   только на loopback; `serve --host` с не-loopback адресом без токена —
   ошибка ввода с кодом 2, а не предупреждение в лог.
4. **Один общий секрет, без состояния.** Никаких сессий, cookie, ролей и
   журнала входов: токен проверяется на каждом запросе и нигде не
   хранится. Ротация — перезапуск с новым токеном.
5. **TLS — не забота продукта.** Сервис рассчитан на обратный прокси или
   приватную сеть; шифрование, HSTS и лимиты — там. Это записано явно,
   чтобы «HTTP с токеном» не читали как «готово в интернет».
6. **Образ ставит только wheel.** `make docker-context` собирает контекст
   из артефактов (`axislar_core`, `agoralar`, плагины), `Dockerfile`
   устанавливает их с `--no-deps` плюс `pydantic`/`packaging`, и запускает
   `serve` от непривилегированного пользователя. Исходников, тестов и
   тулинга разработки в образе нет; данные — в томе `/data`.

## Альтернативы

- **Basic-auth.** Тот же общий секрет, но требует кодирования в каждом
  клиенте и провоцирует хранить пароль в URL. Отклонено.
- **JWT/OAuth.** Нужны ключи, сроки жизни, отзыв — это сервис
  аутентификации, а не продукт. Отклонено до появления нескольких
  пользователей.
- **mTLS.** Сильнее, но требует PKI и настройки клиентов; для одного
  владельца это лишняя инфраструктура. Отклонено (совместимо с прокси).
- **Оставить как было (loopback + документация).** Не даёт запустить в
  контейнере, где loopback снаружи недоступен. Отклонено.
- **Токен в файле конфига.** Секрет попал бы в репозиторий вместе с
  `agoralar.toml`; окружение/флаг оставляют выбор за инфраструктурой.
  Отклонено.

## Последствия

Плюсы: контейнер можно поднять на любом хосте, не открывая данные;
защита включена явно и проверяется тестами; `/health` пригоден для проб.

Минусы: токен виден в `docker inspect`/окружении процесса; нет
пользователей, аудита и отзыва по одному клиенту; TLS обязателен снаружи.
Контейнер работает от `uid 10001`: именованный том создаётся с нужным
владельцем, а bind-mount хостового каталога требует `--user $(id -u)` или
заранее выставленных прав — иначе запись в `/data` падает с `Permission
denied`. Всё это — цена «одного владельца»; пересматривается вместе с M7
(провайдеры/клиенты), если появятся несколько потребителей.

## Статус

Принято, реализовано в 0.13.0. Дополняет ADR-0014 (там зафиксировано
«аутентификации нет» — это решение его отменяет в части auth).
