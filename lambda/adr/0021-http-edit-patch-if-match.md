# ADR-0021: Правка через HTTP — `POST /api/v1/patch` и `If-Match`

## Контекст

Редактор (фаза 3) требует записи через HTTP. Сейчас v1 только читает:
`GET /api/v1/objects*`, `ETag` считается как sha256 от тела и служит лишь для
`304 If-None-Match`. Запись есть только на legacy-маршруте
`PUT /objects/{id}` — без ревизий, то есть две правки (браузер и `curl`)
перетирают друг друга молча.

Ядро к этому готово: `Entity.rev`, `expected_rev`, `ErrorCode.CONFLICT`
(ADR-0024 ядра), в продукте — `bulk_patch` с пообъектными конфликтами и CLI
`patch`/`undo`. Не хватает транспортного слоя и правила, как `ETag`
превращается в `expected_rev`.

## Решение

1. **`ETag` в v1 — из ревизии**: `"r<rev>"`. Не хеш тела: `If-Match` обязан
   давать `expected_rev` без разбора документа, иначе «контент совпал, а
   ревизия другая» неотличимо. Меняется на каждой записи — это честно:
   запись и есть изменение состояния.
2. **`GET /api/v1/objects/{id}`** отдаёт `ETag: "r<N>"`; `If-None-Match` с тем
   же значением → `304` (как сейчас, но по ревизии).
3. **`PUT /api/v1/objects/{id}`** — новый маршрут v1. `id` берётся из пути и
   перекрывает тело. `If-Match`:
   - отсутствует — запись без проверки (импорт, скрипты; поведение как у CLI
     `put`);
   - `*` — объект должен существовать (`expected_rev` — прочитанная ревизия);
   - `"r<N>"` — запись только поверх ревизии `N`.
4. **Несовпадение — `409`** с телом, из которого редактор может показать
   диалог «моё/чужое»:
   `{"error": {"code": "conflict", "message": …, "entity_id": …}, "current": {"etag": "r5", "entity": {…}}}`.
5. **`POST /api/v1/patch`** — массовая правка. Тело:
   `{"ids": [ … ] | "filter": ["axis:op=value", …], "ops": [{"axis", "mode", "values"}], "expected_revs": {"id": rev}, "force": false}`.
   `ids` и `filter` взаимоисключающие. Ответ `200`:
   `{"changed": [{"id", "rev"}], "conflicts": [id], "skipped": [{"id", "axis"}], "errors": […]}` —
   те же поля, что у `bulk_patch`.
6. **Конфликт по объекту не отменяет остальные**: пачка правится пообъектно,
   как в CLI. Атомарность — только у импорта (`bulk_upsert`, ADR-0022 ядра).
7. **Фасеты источника** (`owners=source`) по умолчанию пропускаются и попадают
   в `skipped`; `force: true` переводит владение человеку (ADR-0016). Молча не
   пропускаем (правило 6 гайда).
8. **Паритет с CLI** (ADR-0019): HTTP не даёт ничего, чего нет в терминале;
   обратное тоже верно — поля отчёта совпадают с `patch --apply`.
9. **Доменной логики в `gamma` нет**: разбор тела → `bulk_patch`/`upsert`,
   `ETag` — представление ревизии. Legacy `PUT /objects/{id}` остаётся как был
   (без `ETag`), чтобы не ломать старых клиентов.

## Альтернативы

- **`ETag` как хеш содержимого** (как сейчас). Не даёт `expected_rev`; кроме
  того, no-op перезапись меняет ревизию, но не хеш — `If-Match` пропустил бы
  гонку. Отклонено.
- **`412 Precondition Failed`** вместо `409`. Формально по RFC так, но
  клиенту нужен текущий объект, а `412` не предполагает тело; договорились на
  `409` с `current`, чтобы редактор не делал второй запрос. Отклонено.
- **Атомарный `patch`** («всё или ничего»). Противоречит CLI и смыслу массовой
  правки: один устаревший объект не должен блокировать 300 остальных.
  Отклонено.
- **Метод `PATCH` на коллекции**. Не описан в RFC для коллекций и плохо
  ложится на «фильтр вместо списка». Отклонено.
- **Отдельный `If-Match`-порт в ядре**. `expected_rev` уже есть; новый шов
  ради разбора заголовка — лишняя обязанность для плагинов. Отклонено.

## Последствия

Плюсы: две параллельные правки дают `409`, а не потерю данных; редактор
получает текущее состояние в ответе; правила одинаковы для одного объекта и
пачки; ядро и контракт не меняются.

Минусы: `ETag` теперь инвалидируется на каждой записи (для UI это нормально,
для кэша прокси — чаще `200`); `409` вместо `412` — расхождение с RFC, которое
придётся помнить.

Риски: клиент, который пришлёт `If-Match` со старым хешем (привычка от
прежнего `ETag`), получит `409` — это желаемое поведение, но в CHANGELOG
надо сказать явно.

## Статус

Принято, реализовано в продукте 0.25.0.
