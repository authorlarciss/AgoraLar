# ADR-0014: HTTP как второй транспорт, stdlib, маршруты отделены

## Контекст

Продукту нужен машинный интерфейс помимо CLI: веб-клиенты, интеграции,
будущий UI-плагин. Варианты: FastAPI/uvicorn (две зависимости, ASGI-стек)
или stdlib `http.server`.

## Решение

1. **stdlib `ThreadingHTTPServer`**, ноль новых зависимостей. Для тонкого
   JSON-слоя над `Product` фреймворк не даёт ничего, кроме объёма.
2. **`HttpApi` — маршруты, `make_server`/`serve` — транспорт.** `HttpApi`
   принимает `(method, path, body) -> (status, payload)` и не знает про
   сокеты: маршруты тестируются без сети, сервер — на порту 0.
3. **Ошибки как данные:** 400 — невалидный ввод, 404 — нет объекта/пути,
   405 — метод не тот, 422 — доменные ошибки (`errors[].code`), 413 —
   тело больше 8 МБ. Ни один путь не возвращает трейсбек.
4. **Никакой доменной логики:** `HttpApi` вызывает `Core`/реестр, как CLI.
5. **Безопасность границы:** по умолчанию `127.0.0.1`; наружу — только
   осознанно (`--host`). Аутентификации нет: сервис рассчитан на локальную
   сеть/обратный прокси, и это записано явно.

## Альтернативы

- **FastAPI + uvicorn.** Удобно (валидация, docs), но +2 зависимости и
  ASGI-цикл ради маршрутов, которые помещаются в 150 строк. Отклонено;
  вернуться, если понадобятся схемы OpenAPI и стриминг.
- **Только CLI.** Отсекает интеграции. Отклонено.
- **HTTP внутри ядра.** Ядро не знает про транспорт (ADR-0015 ядра).
  Отклонено.

## Последствия

Плюсы: нулевые зависимости, прозрачный код, тесты без сети и без флаки;
один контракт ошибок для CLI и HTTP.

Минусы: нет автоматической OpenAPI-документации, ручной разбор тела,
нет keep-alive оптимизаций и стриминга; аутентификация — забота
обвязки. Всё это осознанно отложено до момента, когда появится внешний
потребитель.

## Статус

Принято.
