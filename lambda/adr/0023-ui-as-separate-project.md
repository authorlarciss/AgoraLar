# ADR-0023: UI — отдельный проект, продукт — API и реестр плагинов

## Контекст

Сейчас интерфейс живёт внутри продукта: статика лежит в
`nu/gamma/public/static` и едет в колесе `agoralar`, сервер отдаёт её с того
же origin, что и API. Для первого клиента это было правильным решением
(ADR-0019: «UI — первый клиент», паритет с CLI), но у него есть цена,
которая проявится позже:

- интерфейс нельзя заменить, не выпуская новый продукт;
- любой другой клиент (десктоп-оболочка, TUI, бот, чужой фронтенд) обязан
  либо жить в том же репозитории, либо повторять нашу сборку;
- UI и продукт связаны не контрактом, а совпадением версий в одном колесе;
- same-origin-политика (5.7) не даёт подключить UI с другого порта или из
  отдельного проекта — а именно это и нужно для заменяемости.

HTTP API v1 при этом уже есть и покрыт тестами, то есть шов фактически
существует — его надо признать контрактом, а не деталью реализации.

## Решение

1. **API v1 — публичный контракт продукта.** Он версионируется отдельно от
   версии пакета (`API_VERSION = "1"`), отдаётся в `GET /api/v1`, и его форма
   (успешные ответы, ошибки, коды) закрепляется машиночитаемой схемой и
   контрактными тестами. Ломать его можно только мажорным переходом v1→v2,
   с сохранением старого маршрута на время перехода.
2. **Якорь совместимости по образцу `axislar-contract`.** Клиент объявляет,
   с какой версией API работает (`requires_api = ">=1,<2"`); продукт отвечает
   своей версией и внятно отказывает (или предупреждает) при расхождении,
   вместо «пустого экрана».
3. **Внешний UI поддерживается штатно.** `agoralar serve --ui <каталог|URL>`
   и `--allow-origin <origin>` (можно несколько): API отдаёт CORS-preflight,
   изменяющие запросы по-прежнему требуют loopback/allowlist-origin и
   сессионную cookie. Встроенная статика остаётся клиентом по умолчанию, пока
   отдельный проект не выпущен — это fallback, а не единственный путь.
4. **Интерфейс — отдельный проект.** Свой репозиторий, свой пакет, свой темп
   релизов; сборочный шаг (бандлер) допустим и не протекает в продукт.
   Оболочка (pywebview/Tauri) даёт окно и системный диалог папки; путь к
   проекту передаётся по внутреннему каналу, не по HTTP (ADR-0020).
   Продукт при этом остаётся «ядро + реестр плагинов + API»: доменной логики
   в нём не прибавляется, а UI-логики не появляется вовсе.
5. **Порядок работ — сначала швы, потом перенос файлов.** Переписывать UI
   «в новом месте» до того, как API стал контрактом и заработал внешний
   клиент, значит дважды переделывать одно и то же.

### Этапы

| # | Что | Критерий |
|---|---|---|
| S1 | Схема API v1 + `API_VERSION` + контрактные тесты формы ответов и ошибок | клиент может проверить себя без чтения исходников |
| S2 | `--ui`, `--allow-origin`, CORS-preflight, CSRF-правила с allowlist | UI с другого порта работает, чужая страница по-прежнему получает 403 |
| S3 | Якорь `requires_api` и отказ при расхождении | несовместимый клиент видит причину, а не пустой экран |
| S4 | Перенос статики в отдельный проект; fallback в колесе помечен deprecated | внешний UI собирается и обслуживается без пересборки продукта |

## Альтернативы

- **Оставить UI в колесе навсегда.** Дёшево сегодня, но заменяемость
  недостижима: любой другой интерфейс — форк продукта. Отклонено владельцем.
- **Сразу отдельный репозиторий со сборкой.** Правильная цель, но без
  контракта API и внешнего origin получится перенос ради переноса, с
  переделкой. Отклонено как первый шаг.
- **Tauri как основа продукта.** Оболочка лучше всех для установщиков, но
  тянет Rust-тулчейн и сайдкар для Python; продукт не должен зависеть от
  выбора оболочки. Оставлено кандидатом на упаковку.
- **GraphQL/RPC вместо REST.** Гибче для клиента, но доменная модель у нас
  простая, а REST уже покрыт тестами и понятен curl'ом. Отклонено.

## Последствия

Плюсы: интерфейс заменяем, продукт остаётся ядром и реестром; любой клиент
(оболочка, TUI, бот) работает по одному контракту; встроенный UI можно
удалить без ломки API.

Минусы: два проекта и матрица совместимости «UI ↔ API»; CORS и allowlist
добавляют настроек; версия API становится обязательством, которое нельзя
менять «по ходу».

Риски: расхождение версий UI и API. Лечение — якорь из S3 и контрактные
тесты; при мажоре API старый маршрут живёт до релиза нового UI.

## Статус

Принято. Реализация — этапы S1–S4, начиная с S1; перенос статики (S4)
делается после того, как внешний UI собран отдельным проектом.
