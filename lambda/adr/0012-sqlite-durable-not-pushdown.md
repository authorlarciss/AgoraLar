# ADR-0012: SQLite-бэкенд — durable-хранилище, а не SQL-пушдаун

## Контекст

Продукту нужен второй бэкенд. Он проверяет две вещи: (1) механизм плагинов
работает не только для одного встроенного хранилища; (2) контрактный набор
ядра (`run_storage_contract`) действительно достаточен, чтобы сторонний
бэкенд доказал соответствие семантике.

Соблазн — реализовать фильтрацию на SQL (`WHERE` по JSON-полям): это дало
бы «настоящую СУБД», но потребовало бы дублировать семантику модели
(таблица отсутствующих значений, `none_of` на разреженных мультизначных
осях) в SQL-выражениях. Любая ошибка в дублировании проходит контракт,
если контракт проверяет только одну реализацию.

## Решение

1. **SQLite отвечает за долговечность, не за предикаты.** Таблицы:
   `entities(id TEXT PRIMARY KEY, doc TEXT)` и `meta(key, value)`; объект
   хранится как JSON-документ, схема — в `meta`.
2. **Фильтрацию исполняет эталонный движок ядра.** Реализация внутри:
   `build_core()` (memory engine) + загрузка снимка при открытии +
   запись после каждой мутации. Семантика не дублируется по построению.
3. **`capabilities()` честно совпадает с эталоном**: пушдауна нет, но и
   ограничений по типам запросов нет — движок исполняет всё в памяти.
4. **Совместимость проверяется контрактным набором ядра**: тест `tau/delta`
   вызывает `run_storage_contract(lambda schema: SqliteStore(path, schema))`.
5. **Путь пушдауна — отдельный этап.** Когда понадобится, появится
   `Capability.QUERY_PUSHDOWN`: бэкенд объявит его, и контрактный набор
   расширится проверкой «ответы SQL и памяти совпадают» на наборе
   случайных запросов (property-based), а не только на фиксированных кейсах.

## Альтернативы

- **WHERE по JSON-полям в SQL.** Быстрее на больших объёмах, но семантика
  дублируется и расходится с ядром; контракт этого не поймает, пока
  проверяется один бэкенд. Отклонено для v0.
- **Отдельный проект-плагин вместо встроенного.** Правильнее для экосистемы,
  но продукт должен быть полезен «из коробки». Встроенный бэкенд сейчас,
  вынос в отдельный дистрибутив — когда появится `contract-kit` в поставке
  (уже есть в ядре 0.3.0, осталось оформить как отдельный проект).
- **Хранить объекты нормализованно (строки на фасет).** Дороже в миграциях,
  а выигрыш возможен только вместе с пушдауном. Отклонено вместе с ним.

## Последствия

Плюсы: второй бэкенд проходит тот же контракт, что эталон; продукт получает
долговечность без новой зависимости (`sqlite3` в stdlib); семантика модели
остаётся в одном месте; появление пушдауна не потребует менять контракт
модели — только добавить capability и расширить набор.

Минусы: запись переписывает все объекты (как и JSON-бэкенд); на больших
наборах это медленно; контракт пока не проверяет согласованность двух
реализаций между собой (появится вместе с пушдауном).

## Статус

Принято.
